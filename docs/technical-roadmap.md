## 一、演进路线（已规划的 5 条线）

```
① 目标专项攻克（IHookProviderPlugin）    → 插件化，已完成接口  
② AI-Native 提取智能（LLM Bridge）      → 接口待定，可拆卸  
③ 跨平台全终端（Android/iOS/Linux）     → 独立工程  
④ 二进制协议自动逆向（Auto-Re）          → 纯算法  
⑤ 规则市场/分享                         → 插件体系延伸  
```

每条线互不依赖，可并行推进。

### ① 目标专项攻克（当前完成度：接口就绪）

```
核心问题:
  腾讯系 App 有反 Frida 检测 → 通用 Frida 被屏蔽
  → 需要针对特定目标的定制 Hook 方案

当前状态:
  IHookProviderPlugin 接口已定义 ✅
  ProcessHookChannel 已适配 ✅
  缺: 实际插件实现（如 tencent_hook.dll）

插件开发路线:
  V1: 基于 Frida-Gadget 静态注入（非 root 可用）
  V2: 定制 frida-server（改端口+改内存特征）
  V3: 内核级隐藏（LKM 隐藏进程/端口/管道）
```

### ② AI-Native 提取智能（当前完成度：0%）

```
核心问题:
  用户还要手写正则规则 → 门槛高

设计方案:
  LLM Bridge 作为可拆卸插件:
  ├─ 接口: ILlmPlugin（trartget, sample_data）→ Rule[]
  ├─ 本地: Ollama/Qwen（纯本地，数据不出机器）
  ├─ 云端: OpenAI/Claude API（需联网）
  └─ 兜底: 模板引擎（零 LLM）

优先级:
  V1: 规则模板引擎（字段名 → 自动生成正则）       1 周
  V2: LLM Bridge 接口 + Ollama 集成             2 周
  V3: 语义提取（"找支付链接" → 自动识别）         4 周
```

### ③ 跨平台全终端（当前完成度：Android 设计阶段）

```
核心问题:
  当前只有 Windows
  → 限制使用场景

路标:
  V1: Chromium 浏览器扩展（2 周）
      → 在浏览器中直接取解密后的 DOM/API 数据
      → 不需要 CA 证书、不需要代理
      → 覆盖所有 Web 目标

  V2: Android VPN Agent（4-6 周）
      → VpnService 捕获全流量
      → WebSocket 转发到 PC Engine
      → 详见 Android 设计文档

  V3: Linux eBPF TUN（3-4 周）
      → 替代 WinDivert，覆盖 Linux 端游/容器
      → 与现有 TUN 通道共用路由逻辑

  V4: macOS TUN（2 周）
      → utun 接口，与 TUN 通道共用代码
```

### ④ 二进制协议自动逆向（当前完成度：算法研究阶段）

```
核心问题:
  遇到自定义二进制协议 → 看不懂 → 只能 RawData
  世界上没有工具能自动逆向未知协议

设计方案:
  AutoReverseEngine（纯算法，不需要 AI）:
  ├─ 帧检测: 固定长度 / 长度前缀 / 分隔符
  ├─ 字段推断: uint32 / varint / string / float / 枚举
  ├─ 结构重建: TLV / 定长字段组 / 嵌套结构
  └─ 加密检测: 熵值分析 / 模式识别

开发路线:
  V1: 帧边界检测 + 字段类型推断       3 周
  V2: 结构重建 + .proto 格式输出       4 周
  V3: 可逆 TLV 提取 → 自动生成规则    4 周
```

## 二、世界级技术方向研究

以下是当前 DataProbe 还未涉及但全球范围内正在产生突破的领域。

### 方向 A：被动全量 TLS 解密（中国技术世界级水平）

```
现状:
  所有 MITM 工具（Fiddler/Charles/Burp）都依赖主动代理
  遇到证书锁定 + HSTS → 全部失效

世界前沿:
  中国团队在 TLS 被动解密领域有独特积累:
  ├─ 基于内存扫描的 Master Key 提取（不依赖 Hook）
  ├─ 基于分页文件的 TLS 会话恢复
  └─ 基于硬件断点的 SSL 函数截获

DataProbe 可以做的:
  ├─ ProcessHookChannel 的后备方案: 当 Frida 被检测时
  │  改用内存扫描提取 SSL Master Key
  ├─ 不注入进程、不修改内存、不触发反作弊
  └─ 技术来源: Windows 的 PageFile / Process Dump / ETW

难度: ★★★★☆
差异化: 极高——世界上没有工具能做被动 TLS 解密
```

### 方向 B：基于 eBPF 的零损耗捕获（Linux 内核级）

```
现状:
  WinDivert 在 Windows 上做内核级捕获
  Linux 上没有同等工具（iptables TEE 性能差）

世界前沿:
  eBPF（Extended Berkeley Packet Filter）:
  ├─ 在内核中执行沙箱化程序
  ├─ 零拷贝捕获网络包（比 WinDivert 还高效）
  ├─ Linux 5.x+ 原生支持，不需要第三方驱动
  └─ 可捕获 TCP/UDP/ICMP + 附加元数据（PID、进程名）

DataProbe 可以做的:
  ├─ 集成 eBPF 作为 Linux TUN 通道的替代
  ├─ 性能是用户态 TUN 的 10x
  └─ 覆盖 Linux 端游（Steam/Proton）、云原生目标

难度: ★★★☆☆
差异化: 高——eBPF 是网络领域的下一个基础设施
```

### 方向 C：WebAssembly 运行时分析

```
现状:
  越来越多的 App 使用 WASM 做前端加密/混淆
  ├─ 微信/支付宝用 WASM 做支付核心逻辑
  ├─ 端游用 WASM 做反作弊校验
  └─ 传统的字符串扫描 + Hook 对 WASM 无效

世界前沿:
  WASM 逆向工具（wasm-decompile / wasmtime / wabt）:
  ├─ 可以将 WASM 字节码反编译为类 C 伪代码
  ├─ 可以 Hook WASM 函数的导入/导出
  ├─ 可以替换 WASM 函数实现
  └─ 可以追踪 WASM 内存读写

DataProbe 可以做的:
  ├─ ReAnalyzer 扩展: 自动检测 APK/JS 中的 WASM 模块
  ├─ WASM Hook: 替换 WASM 加密函数 → 取明文
  ├─ WASM 解包: 从 APK 中提取 .wasm → 反编译 → 提取常量
  └─ 难度: ★★★☆☆（有成熟的开源工具栈）


差异化: 极高——目前没有安全工具有 WASM 分析能力
```

### 方向 D：程序行为分析（非签名检测）

```
现状:
  当前的反作弊检测只做"签名匹配"
  → 改个名就能绕过 → 滞后

世界前沿:
  基于行为的异常检测:
  ├─ 不是查进程名 → 是查"异常的内存映射"
  ├─ 不是查端口号 → 是查"异常的 IPC 通信模式"  
  ├─ 不是查 DLL 名 → 是查"异常的代码执行流"
  └─ 用于: 检测隐藏的反作弊、检测未知的安全软件

DataProbe 可以做的:
  ├─ AntiCheatDetector V3: 行为检测模式
  ├─ 扫描: 隐藏进程（DKOM）/ 未注册驱动 / 内核回调
  └─ 难度: ★★★★☆（需要内核知识）

难度: ★★★★☆
差异化: 极高——签名检测已死，行为检测是未来
```

### 方向 E：对抗样本与指纹混淆

```
现状:
  JA3 指纹伪造已实现（固定模板）
  但 CDN/WAF 也在不断学习新指纹

世界前沿:
  ┌─────────────────────────────────────────────────────┐
  │  对抗性 TLS 指纹生成:                                │
  │  ├─ 不是使用固定模板 → 是"动态生成"                │
  │  ├─ 每次连接使用不同的密码套件组合                  │
  │  ├─ 模拟真实浏览器的 TLS 参数分布                   │
  │  └─ 使 WAF 无法建立稳定的指纹模型                   │
  └─────────────────────────────────────────────────────┘

DataProbe 可以做的:
  ├─ TlsFingerprintEngine V2: 
  │  ├─ 模板随机化（每个连接用不同的相似模板）
  │  ├─ 参数噪声（在合法范围内随机调整参数顺序）
  │  └─ 对抗更新（跟踪 Cloudflare 新增的指纹黑名单）
  └─ 需要: 持续跟踪 TLS 指纹对抗研究

难度: ★★★★☆
差异化: 高——主动对抗而非静态伪装
```

### 方向 F：后量子 TLS 解密（防御性储备）

```
现状:
  当前 TLS 解密全部依赖传统密码学
  → 后量子密码（PQC）正在标准化，ML-KEM 已成 FIPS

未来:
  3-5 年内主流 TLS 库将默认启用 PQC
  → 所有依赖传统密码学攻击的 MITM 工具将失效
  → DataProbe 的 TLS 解密能力需要重新设计

DataProbe 可以做的（现在是研究窗口）:
  ├─ 跟踪 NIST PQC 标准化进度（ML-KEM / ML-DSA）
  ├─ 评估 PQC 对 MITM 架构的影响
  ├─ 研究混合密钥协商的捕获方案
  └─ 难度: ★★★★★（密码学前沿）

建议: 现在不做，但保持跟踪。
当浏览器默认启用 PQC 时（2027-2028 年），
这是全行业的技术断层，也是重新洗牌的机会。
```

## 四、总结

```
DataProbe 当前覆盖:
  L4-L7 主动捕获 + TLS 解密 + 规则提取 + 插件体系

可以延伸的世界级方向:
  ├─ 被动 TLS 解密（内存扫描 Master Key）    ← 攻防的终极战场
  ├─ eBPF 零损耗捕获（Linux 内核级）         ← 跨平台的基础
  ├─ WASM 运行时分析（新型加密层）            ← 未来 App 的标配
  ├─ 行为检测（反作弊/反检测的进化方向）       ← 攻防对抗的未来
  ├─ 对抗性指纹（让 WAF 无法建立模型）         ← 隐身术的进化
  └─ 后量子 TLS（3 年后的技术断层）            ← 防御性储备

其中 C（WASM）和 E（对抗指纹）是投入产出比最高的:
  C 有成熟开源工具栈，3-4 周可出成果
  E 只需要改指纹模板逻辑，不需要新依赖
  
A（被动 TLS）是最硬但最颠覆的:
  世界上没有工具能做到
  一旦做成 → Fiddler/Charles 等竞品在"不解密 TLS"
  这个功能上永远追不上
```
